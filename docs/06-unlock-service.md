# 06 解锁服务

让控制端在电脑锁屏时输入 Windows 密码或 PIN 解锁。消息格式见 [03](03-protocol.md) 4.6。

## 为什么要单独一个服务

锁屏时，登录界面在系统的安全桌面（Winlogon）上。普通程序（包括被控端）既切不到那个桌面，也没法往里注入按键。只有以 SYSTEM 身份运行的程序，才能在用户会话里打开安全桌面并输入。ToDesk、TeamViewer 也是这样做的。

被控端本身仍以普通用户身份运行，只把解锁请求转给这个服务，其它功能不需要提权。

## 组成

代码在 `host/unlock-service/`：

| 文件 | 作用 |
|---|---|
| `UnlockService.cs` | 服务本体，C# 5，用 .NET Framework 自带的 `csc.exe` 编译，不需要装开发工具。开头一行 `// UNLOCK_SERVICE_VERSION <数字>` 是版本号，见下面"版本号" |
| `install.ps1` | 安装、升级、卸载（`-Uninstall`）。会弹出管理员确认 |

这两个文件跟着被控端安装包走（`resources\unlock-service`），在被控端窗口里点按钮就能装，不用再拷文件、开命令行，见下面"安装与卸载"。

安装后：

- 程序在 `C:\Program Files\RemoteClaude\RemoteClaudeUnlock.exe`，只有管理员能改。程序以 SYSTEM 身份运行，所以文件绝不能放在普通用户能改的位置。
- 服务名 `RemoteClaudeUnlock`，开机自动启动，异常退出后 5 秒自动重启。

## 工作过程

```
控制端 ──数据通道（加密）──> 被控端主进程 ──命名管道──> 解锁服务（SYSTEM，会话 0）
                                                         │ 以 SYSTEM 身份在用户会话里启动
                                                         ▼
                                               注入进程（安全桌面）──按键──> 登录界面
```

密码从控制端到被控端有两条路，到了被控端主进程以后是同一个流程：

- **连着画面时**走数据通道（上图），DTLS 端到端加密，中继和信令服务器都看不到（03 的 4.6）。
- **没连画面时**（手机停在会话列表，被控端 0.9.6 起）走信令通道，要经服务器转发。密码先用被控端这次启动生成的公钥加密，被控端页面把密文原样交给主进程，主进程解开；一条密文只认一次（03 的 2.9，`host/unlockkey.js`）。

1. 被控端连本机命名管道 `\\.\pipe\RemoteClaudeUnlock`，**先核实对面是真的解锁服务**（见下面"管道防冒充"），核实不过就什么都不发，告诉控制端"解锁服务要重新安装"；核实通过才发 `UNLOCK <密码的 Base64>`。
2. 服务检查：密码不含控制字符、长度 1–256；没有另一次解锁正在进行（否则回 `ERR busy`）；15 分钟内失败不到 3 次；当前控制台会话确实处于锁定状态（服务收到过这个会话的锁屏事件且还没收到解锁事件，并且会话里正在运行 `LogonUI.exe`）。不满足就直接返回，不输入任何东西。
3. 服务复制自己的 SYSTEM 令牌、改成用户的会话号，在 `winsta0\winlogon` 桌面上启动自己（`--inject` 模式）。密码通过匿名管道交给它，不出现在命令行里；子进程只继承这一个管道句柄（`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`），服务的其它句柄一个也不带过去。
4. 注入进程：
   1. 切到当前的输入桌面，动一下鼠标唤醒屏幕，再按一下空格收起锁屏画面。
   2. 等 1.5 秒，**再确认一次**：输入桌面必须是 `Winlogon`，会话必须仍是锁定状态。任何一条不满足就退出，不输入密码。这样即使电脑刚好被人解锁了，密码也不会被打进别的窗口。
   3. 按服务的规则再检查一遍密码（含控制字符就退出，一个键都不按）。全选并删掉输入框里已有的内容，逐个字符输入密码（字母、数字、符号用虚拟键，其它字符用 Unicode；控制字符即使漏到这一步也跳过不按），最后按回车。
5. 服务等最多 10 秒，看会话是否变成未锁定，返回 `OK` 或 `ERR still-locked`。

管道命令（每次连接一条，一行文本）：

| 请求 | 回应 |
|---|---|
| `STATUS` | 控制台会话里的程序：`OK locked=1 attach=0 display=0` 或 `OK locked=0 attach=0 display=0`；远程桌面断开、可以接回的会话里的程序：`OK locked=1 attach=1`（见下面"远程桌面断开后从手机接回"）。`display` 是虚拟屏设备（[11](11-virtual-display.md)）：`-1` 没装、`0` 停用、`1` 启用并在运行、`2` 启用了但没能启动（设备管理器里的错误代码 10、43 之类）；`shade` 是隐私屏的黑幕程序在不在运行。这两个版本 3 起才有。旧版服务只回 `OK locked=0/1`，没有 `attach` |
| `DISPLAY ON`、`DISPLAY OFF` | 启用、停用虚拟屏设备（版本 3 起，[11](11-virtual-display.md)），回 `OK`；没装驱动 `ERR no-display`；设备启用了却没能启动 `ERR failed`；控制台测试模式 `ERR no-service`。已经是要的状态就不再动设备。控制台会话里任何程序都能连管道，所以一分钟最多切换 10 次，再多回 `ERR busy`；另一个开关还没做完时等 0.5 秒，还没轮到也回 `ERR busy`。只认控制台会话里的程序 |
| `SHADE ON`、`SHADE OFF`、`SHADE END` | 隐私屏（版本 3 起，[11](11-virtual-display.md) 第 4.4 节）：`ON` 在控制台会话的普通桌面上启动黑幕程序（`--shade`，见下面"隐私屏"），等它盖好黑幕、装好钩子才回 `OK`（最多等 5 秒，没就绪就撤掉、回 `ERR failed`），已经开着就不再开；`OFF` 只撤黑幕；`END` 先锁屏再撤（控制结束时）。另一个还没做完时等 0.5 秒、还没轮到回 `ERR busy`；一分钟里开了 10 次以后再开也回 `ERR busy`。只认控制台会话里的程序 |
| `PING`、`PING display`、`PING shade` | 回 `OK display=<状态> shade=<0|1>`，状态同 `STATUS`。带参数只续那一边的租约，不带两边都续；被控端开着虚拟屏、隐私屏期间各自每 2 秒发一次，一边关没关成就只停那一边的 `PING`，不会替它续着。虚拟屏：看到不是 `1` 就再要一次（被看门狗关了）；开着又 15 秒没收到，服务自己停用（被控端崩了、卡住了、被结束了、用户注销了），停用失败每秒再试。隐私屏：看到 `0` 就当已经撤了（有人按了 Ctrl+Alt+Del）；开着又 15 秒没收到，服务按 `END` 收尾。不和开关抢锁，开关要好几秒时也不排队。只认控制台会话里的程序 |
| `UNLOCK <base64>` | `OK`，或 `ERR <code>`，code 同 03 的 4.6（另一次解锁还没结束时是 `ERR busy`；密码格式不对，包括含控制字符，是 `ERR failed`，不算一次失败）。只认控制台会话里的程序 |
| `ATTACH <base64>` | 把发请求的程序所在的会话接回控制台，接回后还锁着就照常输入密码。回应同 `UNLOCK`。控制台会话里的程序发来时等同 `UNLOCK` |

回应里的字段是空格分开的 `key=value`，被控端忽略认不出的字段，旧版被控端只看开头是不是 `OK`，所以加字段不影响旧版。

服务同时开 4 个处理槽位，每个连接在自己的线程里处理。一个连上不说话、或者隔一会儿才发一个字节拖着不发完的程序，最多占住一个槽位约 3 秒：读一条请求从开始读算起总共只等 2 秒（整行的总时限，不是每次读各等 2 秒），到点回 `ERR failed`；回应后最多再等 1 秒对面关掉。其它槽位照常处理，`STATUS` 照常回应。真正的解锁（以及接回）同一时间只做一次。只服务控制台会话里的程序（`GetNamedPipeClientSessionId`），别的用户、正连着的远程桌面会话里的程序连上就被断开。唯一的例外是远程桌面断开后可以接回控制台的会话，它只能问 `STATUS`、发 `ATTACH`，见下一节。

## 安全措施

- **只在锁屏时动作**：会话没锁就什么都不做；输入密码前在注入进程里再查一次。
- **按键范围有限，但不是"只能输密码"**：管道只接受上面两条命令。注入进程只会按这些键：唤醒用的一下鼠标和空格，清空输入框的 Ctrl+A 和退格，密码里的可打印字符，最后一下回车。含控制字符（U+0000–001F、U+007F、U+0080–009F，比如 Tab、回车、退格、Esc）的密码，在服务和注入进程里都会被拒绝，不会变成切换焦点、提前提交之类的按键。所以借这个管道，没法在安全桌面上切换控件或按任意快捷键。但它仍然会把**任意可打印文字**（最多 256 个字符）打进安全桌面上当前有焦点的输入框，再按一下回车，它并不认得那是不是密码框。能连上管道的本机程序也能做到这一步，所以下面的管道防冒充和失败次数限制仍然重要。管理员确认框只在未锁屏时出现，而服务只在锁屏时动作，借它点不了那个框。
- **管道权限**：只允许本机交互登录的用户和 SYSTEM 访问，拒绝网络访问（ACL 拒绝 NETWORK，并带 `PIPE_REJECT_REMOTE_CLIENTS`）。普通用户只有读写权限，没有"新建实例"权限，不能往这个名字下添自己的管道实例。
- **管道防冒充（服务这边）**：管道名谁先建归谁。如果服务有一刻没握着这个名字，任何普通程序都能建一个同名管道，等被控端把密码送上门。所以服务这样做：
  - 启动时先建一个"锚"实例，带 `FILE_FLAG_FIRST_PIPE_INSTANCE`，名字已经被别的进程占了就失败。这时服务**不提供服务**，在日志和 Windows 事件日志（应用程序日志，来源 `RemoteClaudeUnlock`）里记一条警告，每 5 秒重试，拿回名字后才开始服务。
  - 锚建成后，服务自己连上它，一直握到服务停止。锚不接受别人的连接，只负责让名字一刻也不空出来：干活的实例怎么建、怎么关、出什么错，普通程序都没有抢注的机会。干活的实例也是先建好下一个，再处理当前连接。
  - 管道的所有者明确设成 SYSTEM，普通用户建不出这样的管道。
  - 服务进程给"本机交互登录的用户"开放 `PROCESS_QUERY_LIMITED_INFORMATION`（只能查路径、启动时间这类信息），好让被控端核实它的路径。SYSTEM 进程默认不给普通用户这一项。
- **管道防冒充（被控端这边，`host/unlockpipe.js`）**：被控端不再用 Node 的 `net`，因为它拿不到管道句柄。改用 `CreateFileW` 直接打开管道，并带上 `SECURITY_IDENTIFICATION`：对面只能认出被控端是谁，不能冒用它的身份。连上以后、发任何东西之前，先核实两条：
  - 用 `GetNamedPipeServerProcessId` 拿到对面的进程号，用 `QueryFullProcessImageNameW` 查到的路径必须正好是 `%ProgramFiles%\RemoteClaude\RemoteClaudeUnlock.exe`（只有管理员能往那里放东西）。
  - 管道对象的所有者必须是 SYSTEM（`S-1-5-18`）。光看路径不够：普通用户也能自己以 `--console` 方式运行那个程序，那时管道所有者是这个用户。服务进程的令牌普通用户查不了，管道所有者就是"对面以 SYSTEM 运行"的凭据。
  - 任何一条不满足，就不发 `UNLOCK`，也不发 `STATUS`：页面显示不能解锁，并且和"没装服务"分开，告诉控制端"解锁服务要重新安装"（锁屏状态带 `untrusted: true`，解锁请求返回 `bad-service`，协议文档 4.6，被控端 0.9.28 起；之前的被控端当作没装服务，返回 `no-service`）。日志里记一条"管道对面不是可信的解锁服务"和原因，同一原因只记一次。旧版服务没有开放查询权限，新版被控端会把它当作不可信，升级顺序见下面"安装与卸载"里的"升级"。
- **失败次数**：每个账户 15 分钟内最多失败 3 次，远低于 Windows 默认的账户锁定阈值（阈值设得很低的电脑见下面"远程桌面断开后从手机接回"的注意事项）。按发请求的会话的用户（SID）分开记：别的用户的会话（比如另一个断开的远程桌面会话）输错，不占这个用户的次数；同一个账户的解锁和接回共用一份。查不到 SID 的请求共用一份。注入进程超时被强行结束时，密码可能已经输入，也算一次失败。控制台上的解锁成功后清零这个账户的记录。
- **密码不落地**：手机、服务都不保存密码，谁都不写进日志。被控端只记"解锁成功/失败"。唯一的例外是用户勾了"记住密码"（被控端 0.9.32 起，见下面"记住解锁密码"）：被控端加密后存到服务器上，本机不留。
- **日志**：在 `C:\ProgramData\RemoteClaude\unlock.log`，超过 512 KB 时轮换成 `unlock.log.1`（只留这一份旧的）。这个目录由 `install.ps1` 建好并锁住权限：SYSTEM 和管理员完全控制，普通用户只读。以下几种情况服务一律不写，免得普通用户把 SYSTEM 的写入引到别的文件上：目录或日志文件是重解析点（符号链接、目录联接）；目录所有者不是 SYSTEM 或管理员；日志文件有不止一个硬链接（打开后按句柄检查）。拒绝请求一类的消息（被限流、没锁屏、格式不对、正忙），同类一分钟最多记一条，刷请求刷不满日志。
- **能解锁的人**：要同时有 RemoteClaude 账号（手机已登录）和 Windows 密码。账号密码泄露本身解不了锁。
- **经服务器转发时**（没连画面解锁）：服务器只见到密文；录下密文重发无效（被控端记着用过的密文，重启后换密钥）。服务器要是被换成恶意的、主动把公钥换掉，能骗到密码，这和画面连接的信任前提一样（WebRTC 的证书指纹也经它交换）。

## 远程桌面断开后从手机接回

### 问题

经常用远程桌面（RDP）连到电脑上用。这时被控端和 Claude 跑在远程桌面会话里，不在控制台（电脑自己的显示器）上。关掉远程桌面窗口后，会话变成**断开**状态：程序照常在跑，但没有显示器，被控端采集不到窗口；以前的解锁服务又只理控制台会话里的程序，手机上就显示"没装解锁服务"。手动的办法是在那个会话里以管理员身份运行 `tscon <会话号> /dest:console`，把会话挪到电脑的显示器上，挪过去时是**未锁定**的。

### 做法

控制端（网页、安卓、鸿蒙）和信令协议都不用改，用户照常点"解锁电脑"：

1. 被控端每 2 秒查一次自己所在的会话（`host/sessioninfo.js`，`ProcessIdToSessionId` + `WTSGetActiveConsoleSessionId` + `WTSQuerySessionInformationW(WTSConnectState)`）。会话号不是控制台会话、并且连接状态是 `WTSDisconnected`，就算"远程桌面断开了"（`host/lockstate.js` 的 `isDetached`）。这时对控制端报 `locked: true`（同 03 的 2.9 `host-state` 和 4.6 `lock`，字段不变）；`unlock` 取决于服务对 `STATUS` 的回应里有没有 `attach=1`。正连着的远程桌面会话（Active）不算，照旧只看屏幕锁没锁。
2. 用户在手机上输入密码，被控端发 `ATTACH <密码的 Base64>`（不是 `UNLOCK`）。服务：
   1. 检查发请求的程序所在的会话（下面"谁能触发接回"）。
   2. 用这个会话自己的用户名、域名和收到的密码做一次交互式登录 `LogonUserW(LOGON32_LOGON_INTERACTIVE)`，再用 `WTSQueryUserToken` 取会话的令牌，确认两边是同一个账户（比 SID）。核对在单独的线程里做，最多等 15 秒（域控连不上、Microsoft 账户登录慢时 `LogonUserW` 可能卡很久）；超时就不等了，回 `ERR failed`、算一次失败，那个线程自己跑完、自己关令牌、清零密码缓冲区。核对有了结果但没通过，也算一次失败、不接回，并且**不论是哪种错误都回 `ERR still-locked`**（只有上面的超时回 `ERR failed`）：密码不对（1326），和密码其实对了但账户受限（1330 密码过期、1907 必须改密码、1909 账户已锁定、1331 账户停用、1385 没有本地登录权限等）回的一样，回应不透露密码对没对；准确的错误码只写在 `unlock.log` 里。
   3. 再检查一次第 1 步（核对密码期间情况可能变了），然后 `WTSConnectSessionW(会话, 控制台会话, 密码, bWait = FALSE)` 把会话接到电脑的显示器上：请求发出就返回，不在持锁时干等会话切换；**成没成只看之后轮询到的控制台会话号**。先不带密码，5 秒内没到控制台，就重新检查接回条件、带上已核对过的密码再试一次，最多再等 10 秒。控制台正处在切换中（会话号为 `0xFFFFFFFF`）、或者重新检查时条件已经不满足（比如第一次请求正在接，会话已经不是断开状态），就不再发请求，只接着等；第一次请求只是慢的话，两次请求会同时在途，成没成照样只看轮询。
   4. 会话到了控制台以后，最多等 5 秒看会话里有没有登录界面（`LogonUI.exe`）。这一步**不靠锁屏事件**：平时判断锁屏要求服务收到过这个会话的 `SessionLock` 事件（见上面"工作过程"第 2 步），可远程桌面断开、接回时 Windows 不一定发这个事件，服务重启后也不记得非控制台会话锁过屏。所以锁屏事件和 LogonUI 都有就马上输入；否则等满 5 秒，那时有 LogonUI 就当锁着，按 `UNLOCK` 的流程输入密码（锁没锁、解没解开都只看 LogonUI）；一直没有才回 `OK`。宁可多输一次密码，也不早早回 `OK`。接回路径上不清零失败记录，只有控制台上的解锁成功才清。
3. 被控端发现自己回到控制台，状态变回未锁定，推给控制端；页面把所有连着的画面重新采集一次（断开期间画面不一定报"停了"，分辨率也换了）。输入、剪贴板每次都现查前台窗口，不用特别处理。

回给控制端的码都是 4.6 里已有的：`ok`、`still-locked`（密码核对没通过，包括密码对了但账户受限）、`rate-limited`、`busy`、`failed`（不满足接回条件、核对超时或接回失败）、`no-service`（旧版服务或没装服务）。没有新码。服务最坏要约 65 秒（核对 15 + 接回 5 + 10 + 等登录界面 5 + 输入密码约 30），被控端给 `ATTACH` 的超时是 75 秒。

### 谁能触发接回

服务只在这些条件全都满足时接回，否则回 `ERR failed` 并在日志里写明原因：

- 要接回的会话就是发请求的程序所在的会话。会话号由 `GetNamedPipeClientSessionId` 给出，请求里不带会话号。
- 这个会话处于 `WTSDisconnected`。`WTSActive`（有人正连着远程桌面在用）不接，免得把正在用的远程桌面抢走。会话 0（服务用的，它也显示为断开）永远不接。
- 这个会话有登录用户（`WTSUserName` 不为空）。
- 控制台此刻有会话（`WTSGetActiveConsoleSessionId` 不是 `0xFFFFFFFF`），并且上面没有别的用户：只有登录界面（没有用户），或者是同一个用户而且锁着。
- 失败次数限制和解锁共用、按账户分开（这个会话的用户 15 分钟内失败 3 次就回 `rate-limited`），另外接回本身 15 分钟内最多 5 次（不论成败，所有账户合计）。和解锁共用一把锁，同时只做一件；锁里可能卡很久的两步都有时限（核对密码最多等 15 秒；接回请求不等完成，之后最多轮询 15 秒）。

不满足条件的非控制台程序，连 `STATUS` 都得不到回应（和以前一样直接断开）；满足条件的也只认 `STATUS`、`ATTACH`，发 `UNLOCK` 回 `ERR failed`：往安全桌面输入密码仍然只为控制台会话做。输入密码前服务还确认控制台会话仍是请求的那个会话，注入进程也确认自己就在控制台会话里，控制台中途换了会话就不输入。

### 为什么接回前要核对 Windows 密码

不核对也能接回：服务以 SYSTEM 运行，`tscon` 以 SYSTEM 运行时不要密码。但那样的话，只要有手机上的 RemoteClaude 账号（比如手机丢了、账号密码泄露），就能：

- 把这个用户**未锁定**的桌面亮到电脑的显示器上，被在电脑跟前的人看到、操作；
- 接回后被控端恢复采集，远程看到、操作 Claude 窗口。

这等于没有 Windows 密码就"解锁"了电脑，和普通锁屏的前提（"要同时有 RemoteClaude 账号和 Windows 密码"）不一致。所以要求先核对密码。代价：

- **只认账户密码，不认 PIN**。Windows Hello 的 PIN 绑定在本机 TPM 上，只有登录界面能核对，服务没有办法核对。远程桌面断开后从手机接回时，**要输入 Windows 账户密码**（远程桌面登录用的那个，Microsoft 账户就是它的密码），不能输 PIN。输入 PIN 会核对不过，提示"没解开，请检查密码或 PIN"，并算一次失败。接回后如果还锁着，服务输入的也是这同一个密码，登录界面认账户密码，所以没问题。
- 核对失败会在 Windows 安全日志里留一条登录失败（4625），**也计入 Windows 的账户锁定计数（badPwdCount）**，和在锁屏上输错一样。服务自己每个账户 15 分钟 3 次的限制远低于默认阈值；但如果这台电脑（或域策略）的账户锁定阈值设得很低（3 次或更少），服务放行的几次失败，加上在锁屏、远程桌面上输错的，可能先把账户锁住，那时连正确的密码也会回"没解开"，要等锁定时间过去或由管理员解锁。用 `net accounts`（域账户问管理员）可以查看阈值；阈值很低的电脑，手机上输错一两次就先停下来确认密码。
- 用的是交互式登录：账户要有"允许本地登录"的权限。接回控制台本来就是在电脑跟前登录，这个要求是对的。

### 剩下的风险

- **会话里已经在运行的恶意程序**（以这个用户身份运行）也能连上管道发 `ATTACH`。它不知道密码就接不回；它要是已经知道密码（比如记录了键盘），本来就能自己运行 `tscon` 把会话挪到控制台（同一个用户不需要密码），服务没有给它多出能力。所以这一条可以接受。
- 被控端的检查（核实管道对面是真服务）和以前一样，冒充服务骗密码的风险不变。
- 接回后电脑的显示器上就是这个用户的桌面（断开前没锁的话）。这是用户在手机上主动要的，和在跟前 `tscon` 一样；建议用户确认电脑跟前没有别人。
- **接回会抢走电脑跟前的登录界面**：控制台停在登录界面（没有用户）时才允许接回，可服务看不出有没有人正坐在电脑跟前、在登录界面上输入密码。这时接回，显示器会直接换成远程会话的画面（锁着的话是它的锁屏），跟前那个人输了一半的内容就没了，他要登录得再切换用户。手机上解锁前请确认没人正在用这台电脑。
- **管道的 ACL 挡不住远程桌面会话**：管道允许 INTERACTIVE（本机交互登录的用户），远程桌面登录的用户也带这个 SID，所以远程桌面会话里的程序能打开管道。挡住它们的是服务按会话号做的检查（`GetNamedPipeClientSessionId`）：不在控制台、又不是可以接回的断开会话，连上就断开；可以接回的也只认 `STATUS`、`ATTACH`。
- 密码核对通过以后，如果接回条件恰好变了或者接回没成，回的是 `ERR failed`，和密码不对的 `ERR still-locked` 不同，会话里的程序能由此知道密码是对的。接回成功回 `OK` 本来也说明了这一点，次数又受限，所以不再统一；要统一的只是核对这一步（账户受限和密码不对回同一个码）。
- 失败次数按账户分开以后，几个账户各有自己的 15 分钟 3 次。每个账户能试的次数和以前一样；只是不同账户的失败不再互相挤占。
- 核对密码超时（15 秒）以后服务不再等那个线程，它在后台自己跑完。每次超时算一次失败，所以同一个账户 15 分钟内最多留下 3 个这样的线程。锁里可能卡很久的两步都有时限：`LogonUserW` 最多等 15 秒，`WTSConnectSessionW` 不等完成（之后轮询最多 15 秒）。所以一次接回最多占着锁约 65 秒（见上面的耗时），别的解锁请求最多回 `busy` 这么久，不会一直回 `busy`。其余在锁里调用的是本机的会话查询（`WTSQuerySessionInformationW`、`WTSQueryUserToken`），没有另设时限。

### 兼容

| 被控端 | 服务 | 远程桌面断开时 |
|---|---|---|
| 新 | 新 | 显示锁屏、可以解锁，解锁即接回 |
| 新 | 旧 | 旧服务直接断开非控制台的连接，`STATUS` 没回应：显示锁屏、不能解锁（"没装解锁服务"） |
| 旧 | 新 | 旧被控端不认断开状态，按屏幕锁没锁报；新服务对它的 `STATUS` 回 `OK ... attach=1`，旧被控端会以为能解锁，发 `UNLOCK` 得到 `failed`。两边一起升级即可 |
| 旧 | 旧 | 和以前一样，用不了 |

在控制台上时，新旧组合的行为都和以前一样（`STATUS` 多出的 `attach=0` 旧被控端不看）。

### 参考的微软文档

- [WTSConnectSessionW](https://learn.microsoft.com/en-us/windows/win32/api/wtsapi32/nf-wtsapi32-wtsconnectsessionw)：`LogonId` 是要接过去的会话，它的输出转到 `TargetLogonId`；密码是 `LogonId` 那个用户的，"调用者和会话是同一个用户时可以为空"，不能是 NULL。文档**没写** SYSTEM 调用时要不要密码、原来在控制台上的会话会怎样、接过去后锁不锁。所以服务先不带密码、再带核对过的密码，并且接回后自己检查锁没锁。
- [tscon](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/tscon)：`/dest` 指定的会话会被断开；连接别人的会话要密码，自己的不用。
- [WTSQuerySessionInformationW](https://learn.microsoft.com/en-us/windows/win32/api/wtsapi32/nf-wtsapi32-wtsquerysessioninformationw)、[WTS_INFO_CLASS](https://learn.microsoft.com/en-us/windows/win32/api/wtsapi32/ne-wtsapi32-wts_info_class)、[WTS_CONNECTSTATE_CLASS](https://learn.microsoft.com/en-us/windows/win32/api/wtsapi32/ne-wtsapi32-wts_connectstate_class)：`WTSConnectState`（`WTSDisconnected` = 4）、`WTSUserName`、`WTSDomainName`；`WTSClientProtocolType` 为 0 表示在控制台。查别的用户的会话要有查询权限，SYSTEM 有。
- [WTSGetActiveConsoleSessionId](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-wtsgetactiveconsolesessionid)：控制台正在接上或断开时返回 `0xFFFFFFFF`。
- [LogonUserW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-logonuserw)：交互式登录要求账户有 `SE_INTERACTIVE_LOGON_NAME`；只有登录 Microsoft 账户（文档里的 Passport）才要 `SE_TCB_NAME`，SYSTEM 有。
- [Remote Desktop Services permissions](https://learn.microsoft.com/en-us/windows/win32/termserv/terminal-services-permissions)：Connect 权限是"连接到另一个会话"。
- [GetNamedPipeClientSessionId](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeclientsessionid)：管道客户端所在的会话。

## 虚拟屏（版本 3 起）

设计和实测见 [11](11-virtual-display.md)。这里只记和服务、安装有关的部分。

- **驱动**：VirtualDrivers/Virtual-Display-Driver 25.7.23（MIT），文件在 `host/unlock-service/vdd/`（`MttVDD.dll`、`MttVDD.inf`、`mttvdd.cat` 原样来自 `VirtualDisplayDriver-x86.Driver.Only.zip`，`vdd_settings.xml` 是我们的，`LICENSE` 是它的许可证）。`.cat` 的签名包含 `.inf` 的哈希，所以这几个文件在 `.gitattributes` 里设成了二进制，不做行尾转换。
- **安装**（`install.ps1`，服务装好、启动以后）：把这几个文件复制进 `Program Files\RemoteClaude\vdd`，核对四个文件的 SHA256（写死在脚本里，`vdd_settings.xml` 也在内）和两个驱动文件的签名（必须是 SignPath Foundation 签的、有效）。然后先在 `HKLM\SOFTWARE\MikeTheTech\VirtualDisplayDriver` 写 `VDDPATH`，指向 `Program Files\RemoteClaude\vdd`：驱动从那里读设置，不写就读 `C:\VirtualDisplayDriver`，那个目录普通用户能建、能往里放文件，装的时候驱动会启动一次，所以要先写。再运行 `RemoteClaudeUnlock.exe --install-display <inf>`：建一个硬件 ID 为 `Root\MttVDD` 的根设备、装驱动，装完停用。没装成或者发现是别人的驱动时，`VDDPATH` 改回原来的值。Windows 第一次装这个发布者的驱动会问一句，点"安装"即可，不要勾"始终信任"：勾了会把 SignPath Foundation 的证书加进本机的"受信任的发布者"，以后它签的驱动都不再问。
- **脚本里写死的哈希**只防"复制进安装目录以后被换掉"，防不了改脚本本身：`install.ps1` 和以前一样放在普通用户能改的位置，见上面"点按钮安装，信任的是被控端自己的安装目录"。
- **只管自己建的设备**：建好的设备的实例 ID 记在 `HKLM\SOFTWARE\RemoteClaude` 的 `DisplayDevice` 里，服务只启用、停用它。电脑上已经有别的程序或用户自己装的同一个驱动（硬件 ID 一样、实例 ID 不是记下的那个）时，`--install-display` 什么都不做，退出码 2，`VDDPATH` 也不写。
- **驱动没装上**只警告、不回滚：解锁服务已经装好了。窗口留着等回车，让人看到原因。
- **卸载**（`install.ps1 -Uninstall`）：`--uninstall-display` 先停用再删设备（设备开着时直接删，要重启才完全消失）；它失败了就不往下卸服务，免得没有看门狗以后虚拟屏一直开着。再用 `pnputil /delete-driver` 删驱动包，不加 `/uninstall`、`/force`：别的设备还在用时 pnputil 会拒绝，不会把它从别人的设备上卸掉。`VDDPATH` 指着我们的目录时删掉它。
- **服务启动时**如果虚拟屏开着（服务被结束、电脑开着虚拟屏重启了），先停用：这时还没有被控端要求开着。**服务停止时**也停用：之后没有看门狗了。
- **建设备和记实例 ID 之间出错**（写不进注册表）：把刚建的设备删掉，否则它下次会被当成别人的，再也装不上。
- **驱动自己的管道**：驱动加载后会建一个 Everyone 都能读写的命名管道 `\\.\pipe\MTTVirtualDisplayPipe`，可以改屏幕数量、重载驱动；它没有拒绝网络访问，有这台电脑账户密码的人也可能经网络连上。设备平时停用，驱动不加载，这个管道也就不在；只在控制期间开着虚拟屏时存在。我们没有去改它的权限：管道是驱动自己建的，每来一个连接它都会建新的实例，改一次不一定管用，没有试过。

## 隐私屏（版本 3 起）

设计和实测见 [11](11-virtual-display.md) 第 4.4、5.2 节。

- **黑幕程序**就是服务程序本身，用 `--shade locked|unlocked <就绪事件名>` 启动（第一个参数是启动时会话锁着没有）：服务复制自己的 SYSTEM 令牌、改成控制台会话号，在 `winsta0\default`（普通桌面）上启动它，和注入进程一样只继承一个标准输入的管道句柄。以 SYSTEM 身份运行，电脑前的普通用户结束不了它，低级钩子也挡得住提了权的窗口。
- **就绪**：服务每次新建一个 `Global\RemoteClaudeShadeReady-<随机>` 事件，只有 SYSTEM 能打开；黑幕程序铺好黑幕、装好钩子后把它设上，服务等到了才回 `OK`，被控端这时才输密码。会话里的普通程序设不上它，冒充不了"盖好了"。
- **它做的事**：每块屏一块黑幕（`WS_POPUP`，`TOPMOST|TRANSPARENT|TOOLWINDOW|LAYERED|NOACTIVATE`，不透明，`WDA_EXCLUDEFROMCAPTURE`）。上半屏写"这台电脑正在被远程操作"，下半屏写电脑前的人怎么退出（按 Ctrl+Alt+Del、再选"锁定"或按 Esc，电脑会锁屏，用自己的密码登录），以及远程的人可以在 App 的菜单里关掉。每 0.25 秒重新置顶一次；插拔显示器、改分辨率时先铺好新的再撤旧的，中间不留空档；挪到缩放不同的屏上时改回铺满。低级键盘、鼠标钩子挡掉 `dwExtraInfo` 不是 `0x52434C44`（"RCLD"）的输入。被控端（`host/win32.js`）和注入进程注入时都带这个标记。
- **钩子**装在一个专门的线程上，只跑消息循环（回调慢了 Windows 会悄悄摘掉低级钩子，界面线程卡一下就可能发生）。没锁屏、在普通桌面上时每 2 秒自检一次：发一个不带标记的空键码（`0x9F`，没分配的虚拟键码，键盘上没有，也不会有程序拿它当热键）和一下右、一下左的鼠标移动，被钩子挡下，光标不动；下一次看两个钩子都挡下过输入没有（电脑前的人动了键鼠也算）。没收到就重装钩子、记日志，**不锁屏**；`SendInput` 没发出去（桌面正好在切换）那一轮不算。重装时先装新的再摘旧的，中间不留空档；新的装不上马上锁屏退出。原来是"连着两次没收到就锁屏"，2026-11-24 真机上开隐私屏 8 秒后被锁了屏，正好是这个时间，当时以为是误报，先改成只重装、记日志。之后的复测（21:29–21:31，黑幕前后开了一分半钟，约 45 轮自检）日志里一次"没收到"都没有，黑幕程序自己的日志也确实写得进去，所以 20:37 那次多半不是自检误报（可能是电脑前有人按了 Ctrl+Alt+Del；那时还没有"为什么锁屏"的日志，查不清）。保持只重装、不锁屏。钩子被系统悄悄摘掉本来就少（回调在专门的线程上，不会慢），重装就补回来了。钩子一开始就装不上：先锁屏，再退出（退出码 8）。
- **退出**：标准输入读到 `OFF` 撤黑幕退出（退出码 6）；读到 `END` 或者标准输入断了（服务没了），先 `LockWorkStation`、等到锁屏通知、再盖 0.8 秒等锁屏画面出来才撤（退出码 0）；锁不上就 `WTSDisconnectSession` 断开这个会话，屏幕回到登录界面（退出码 7）；断开也不成功就留着黑幕，过一会儿再试。每次锁屏退出都在日志里写明原因（控制结束、有人按了 Ctrl+Alt+Del、钩子装不上）。黑幕程序出了任何没接住的异常，先锁屏、等登录界面（`LogonUI`）出来再盖 0.8 秒（不行就断开会话）再退出（退出码 8）。没走到任何一个退出点、消息循环就结束了的，退出码 9。
- **服务收尾**：等黑幕程序退出最多 8 秒，等不到时 `END` 先断开会话、再结束它，桌面一刻也不露出来；断开也失败只能记日志、照样结束它（不然电脑前的键盘鼠标一直被挡着）。黑幕程序盖好过黑幕、又不是正常退出的（不是 0、6、7、8：崩了、被人结束了）、会话又没锁着，服务就断开这个会话；没就绪就退出的不断开（桌面本来就没盖）。进程句柄由一把小锁护着，别的线程（`PING`、`STATUS`）问的时候不会碰到已经关掉的句柄；看门狗里出了异常只记日志，线程不停（虚拟屏的租约也靠它看）。
- **Ctrl+Alt+Del**：系统不让程序拦这个组合键。会话没锁着、解锁后已经回到过普通桌面、输入桌面却切到了安全桌面（Ctrl+Alt+Del、管理员确认框），黑幕先留着（在安全桌面上锁不了屏），等回到普通桌面就锁屏退出；这期间会话被锁了（点了"锁定"）就直接退出。"解锁后已经回到过普通桌面"这一条是为了远程解锁：那一刻解锁通知可能比输入桌面切回普通桌面先到。没锁屏时启动、那一刻正停在安全桌面上的，回到普通桌面也锁屏。
- **锁屏状态**跟着会话的锁屏、解锁通知（`WTSRegisterSessionNotification`）走，不看输入桌面的名字：刚锁上时锁屏画面还在普通桌面上，看名字判断不准（docs/11 第 3.3 节踩过）。启动参数是服务启动它之前看的，登记完通知再核对一次；之后每秒核对：以为锁着、却连着 2 秒在普通桌面上、也没有登录界面在跑，就是漏了解锁通知，改成没锁。
- **会话**：黑幕只算在控制台会话里的（`STATUS`、`PING` 的 `shade=`）。切换了用户、黑幕还在原来的会话里时算 `0`；再要 `ON` 时先把原来那个撤掉（只撤不锁：那个会话已经不在显示器上，接回要输密码），再在现在的会话里开。
- **看门狗**：黑幕程序自己退出了（有人按了 Ctrl+Alt+Del）就收拾句柄、记日志；被控端 15 秒没为隐私屏报平安（`PING shade`）就按 `END` 先锁屏再撤。服务停止时也按 `END`。
- **挡不住的**：
  - 触摸屏、手写笔的输入：低级鼠标钩子只看得到模拟成鼠标的那部分，直接的触摸、笔输入挡不住。
  - 带 UIAccess 的程序（屏幕键盘、讲述人之类辅助工具）的窗口可以盖在黑幕上面。
  - 控制台会话里的程序都能连管道发 `SHADE`、`PING`：本机的程序可以打开隐私屏挡住键盘鼠标（一分钟最多开 10 次，按 Ctrl+Alt+Del 就能退出），或者替被控端续着租约。它本来就在这个会话里、看得到桌面，没有多拿到什么。
  - 隐私屏开着时电脑锁了屏（按了 Win+L，或者从手机锁定），电脑前的人在锁屏界面上自己输密码解开，看到的还是黑幕：要按黑幕上写的 Ctrl+Alt+Del 退出、再登录一次。控制结束前再从手机解锁，又会盖上。
- **编译**多了 `System.Windows.Forms.dll`、`System.Drawing.dll` 两个引用（`install.ps1`）。

## 记住解锁密码（被控端 0.9.32 起）

用户 2026-11-24 提的：输对一次以后，下次从手机解锁不用再输。消息见 [03](03-protocol.md) 2.9"记住解锁密码"。

- **存在哪**：手动输密码解开了、解锁框里勾着"记住密码"（默认勾）时，被控端用 Electron 的 `safeStorage`（Windows 上是 DPAPI：只有这台电脑上这个 Windows 用户解得开）加密，密文经信令连接（`unlock-secret`）存到服务器上这台电脑名下（`unlock_secrets` 表），被控端本地不留。被控端连上服务器时取回密文，只放在内存里，用时才解开。
- **两边各一半**：服务器只有密文、解不开；电脑只有钥匙、没有密文。拖库拿不到密码，电脑的硬盘被拿走也拿不到（密文不在上面）。
- **怎么用**：手机点"解锁"时，电脑记着密码（`lock.saved`）就不弹输入框，直接让电脑用记下的密码解锁，只试一次。还是锁着（`still-locked`，多半是改过密码）：被控端删掉记下的、回 `saved-wrong`，手机弹输入框让用户手动输，输对了再记新的。
- **删掉**：解锁框里不勾"记住密码"输对了、手机菜单里"忘掉记下的解锁密码"、解不开（换了 Windows 用户、被控端的资料目录被清过）、电脑退出登录、账号重置密码。
- **代价**：
  - 以后能登录这个账号的人，不知道 Windows 密码也能从手机解开这台电脑。
  - 服务器被攻破、或者被换成假的：它能冒充手机发"用记下的密码解锁"，不用登录账号也能解开电脑（安全审查 2026-11-24 指出）。原来服务器只经手公钥加密过的密码，被动地拿不到，主动冒充也只能在用户下次输密码时把公钥换掉。服务器被攻破本来就能冒充手机看画面、操作没锁的电脑，多出来的是能把锁着的解开。要堵上得让每部手机各存一把钥匙、解锁时带上，代价是只有当初记密码的那部手机能自动解锁，没做。
  - 输错次数照样算：记下的不对时用掉一次（15 分钟 3 次），之后手动输的机会少一次。
- **对不上号的回应**：服务器按顺序回，被控端按顺序认领；要删的没删成（断线、服务器出错）记着，下次连上先删再取，取回来的旧密文不认。服务器回来的密文先核对格式和长度。服务器每小时清一次没有登录令牌的电脑记下的密文。
- **实现**：`host/unlocksecret.js`（测试 `host/test/unlocksecret.test.js`），服务器 `server/lib/hub.js` 的 `unlockSecret`、`server/lib/store.js` 的 `unlock_secrets`。

## 不支持的情况

- 要求先按 Ctrl+Alt+Del 的电脑（组策略"交互式登录：无须按 Ctrl+Alt+Del"被关掉）。会返回 `still-locked`。
- 只设置了人脸、指纹而没有 PIN 或密码的账户。
- 多个用户共用一台电脑、锁屏界面停在别的用户上。
- 远程桌面断开时：电脑跟前有别的用户登录着（不接回）；只设了 PIN 而记不得账户密码；Azure AD（Entra）账户可能核对不过（会话的域名是 `AzureAD`，`LogonUserW` 不一定认），需要在那样的电脑上实测。

## 安装与卸载

### 在被控端窗口里装

被控端窗口里有一栏"从手机解锁"，显示解锁服务的状态，旁边的按钮跟着变：

| 状态 | 按钮 | 意思 |
|---|---|---|
| 没装 | 安装 | Program Files 里没有装过的源码 |
| 已装好 | 重新安装 | 管道那头的服务通过了核实，可以从手机解锁 |
| 有新版本 | 更新 | 被控端带的服务比装着的新（见下面"版本号"），窗口日志里也会提示一次 |
| 要重新安装 | 重新安装 | 管道那头的服务核实不过（多半是 0.9.25 之前装的旧版） |
| 没有响应 | 重新安装 | 装过，但管道没有回应，多半没在运行 |

点按钮后弹一次管理员确认，接着弹出一个 PowerShell 窗口，照常核对、编译、安装（就是下面"安装脚本"做的事，只是不用再输 `y`）。装好了窗口自动关掉；出错时窗口留着，看完原因按回车关掉。被控端随后从管道核实新服务，在窗口日志里写结果：装好了、管理员确认被取消了、失败了（带安装脚本的退出码），或者脚本说装好了但服务没回应、没通过核实。

被控端是这样调用的（`host/unlockinstall.js`）：

- 源码和安装脚本由 electron-builder 的 `extraResources` 放在安装目录的 `resources\unlock-service` 里，不进 asar（PowerShell 和 C# 编译器要读真的文件）。开发时（`npm start`）用的就是 `host\unlock-service`。
- 算出自带的 `UnlockService.cs` 的 SHA256，在隐藏的窗口里运行 64 位 Windows PowerShell 5.1：`install.ps1 -FromHost -ExpectSha256 <哈希>`。
- `-FromHost` 让脚本不管现在是不是管理员，都在新窗口里以管理员身份重新打开自己（带上 `-NoPause`：装好了不等回车），等它结束，按它的退出码退出：`0` 装好了，`1` 失败，`2` 没能以管理员身份打开（多半是确认框里点了"否"）。总是开新窗口，是因为被控端那个窗口是隐藏的，出错时没人看得到，脚本等回车也会一直卡着。
- 退出码是 `0` 时，被控端每秒问一次 `STATUS`，最多 10 次，回 `OK` 且通过上面"管道防冒充（被控端这边）"的核实才算装好；然后马上重新查一次锁屏状态，控制端看到的"能不能解锁"跟着变。

点按钮安装，信任的是被控端自己的安装目录：

- 被控端装在用户自己的目录（`%LOCALAPPDATA%\Programs\remote-claude-host`）里，这两个文件普通用户改得了，就像以前仓库目录普通用户改得了一样。以普通用户身份运行的恶意程序可以改掉它们，等你下次点按钮、在管理员确认框里点"是"时拿到 SYSTEM，确认框上只显示"Windows PowerShell"，看不出区别。这一点和以前手动运行一样（`install.ps1` 本来就是从普通用户能改的位置以管理员身份运行的），能改它们的程序也本来就能改被控端本身。
- 和手动运行比少了一步：手动运行时会打出哈希等你核对后输 `y`，点按钮时哈希由被控端自己算，不再让人核对。所以这一步只保证"编译的就是被控端算过哈希的那一份"：安装脚本照旧先把源码复制进只有管理员能改的安装目录、核对哈希再编译，算完哈希以后再被换掉的会被拦下；它不能证明这份源码没被人改过。
- 要防这一类，得给这两个文件签名、安装脚本提权后先验签名，或者把被控端改成装在只有管理员能改的位置，现在都没做。

### 版本号

`UnlockService.cs` 开头有一行 `// UNLOCK_SERVICE_VERSION <数字>`。被控端读 Program Files 里装着的那份源码（安装脚本放的，普通用户能读）和自带的那份，自带的版本号大，就显示"有新版本"。

- 只比内容是否一样不行：电脑上装的可能比被控端带的还新（比如从别的分支装的），那时提示"更新"就把它换旧了。版本号一样或装的更大，都不提示。
- 加版本号之前装的源码没有这一行，版本号算 0；但除了这一行以外和自带的一样（不管行尾）就算已是最新，不用为了多一行注释重装。
- **改了 `UnlockService.cs` 就要把版本号加 1**，否则已经装了这个版本号的电脑不会提示更新。`host/test/unlockinstall.test.js` 里给每个版本号登记了源码的哈希，改了源码没加版本号、或者加了没登记，测试都会失败，并提示怎么改。

### 手动运行安装脚本

被控端打不开、或者想在仓库里直接装时，照旧可以手动运行。在电脑上以普通身份运行，脚本会弹出管理员确认：

```powershell
powershell -ExecutionPolicy Bypass -File host\unlock-service\install.ps1
```

卸载（被控端窗口里没有卸载按钮，虚拟屏驱动一起卸掉）：

```powershell
powershell -ExecutionPolicy Bypass -File host\unlock-service\install.ps1 -Uninstall
```

装了被控端的电脑上，脚本在 `%LOCALAPPDATA%\Programs\remote-claude-host\resources\unlock-service\install.ps1`，把上面命令里的路径换成它就行。

被控端每 30 秒问一次服务在不在，手动装好后不用重启被控端。

### 安装脚本

安装脚本只在以管理员身份运行的 64 位 Windows PowerShell 5.1 里干活，否则会用它重新打开自己。程序装在 64 位的 Program Files（`%ProgramW6432%`）里，和被控端核实的路径一致。

重新安装时，脚本先把源码复制到安装目录里的临时文件名、核对哈希、编译成临时的 exe，都成功了才停掉旧服务、换上新程序、建服务。在这之前取消（不输 `y`）、`-ExpectSha256` 不一致、编译失败，原来的服务照常运行、程序文件不变，临时文件会删掉。停旧服务以后出错时：换程序时原来的 exe 先改名成 `RemoteClaudeUnlock.old.exe` 备份，新程序就位失败就改回去；脚本再看服务的实际状态，服务还注册着、程序也在，就试着把它重新启动起来，并说清用的是原来的还是新编译的程序；服务注册已经删掉的，提示处理后重新运行脚本。

安装脚本还会做两件事：

- 建好 `C:\ProgramData\RemoteClaude` 并锁住权限。权限用 SID 设置，中文 Windows 上也适用。如果这个目录已经存在，并且它是链接、所有者不是管理员或 SYSTEM，或者里面有子目录、链接、普通用户放进去的文件，就把整个目录改名挪开（`RemoteClaude.untrusted-时间`，不删除、不跟随链接），再建一个新的，并提示用户确认后自行删除。
- 装好后打印 `sc qc RemoteClaudeUnlock`。请核对 `BINARY_PATH_NAME` 带引号、指向 Program Files，`SERVICE_START_NAME` 是 `LocalSystem`。

卸载时保留日志目录。

### 升级

解锁服务是单独装的 Windows 服务，不随被控端自动升级。被控端 0.9.25 起发命令前要核实管道对面（上面"管道防冒充（被控端这边）"），在那之前装的解锁服务没开放查询权限、管道所有者也不是 SYSTEM，过不了核实。被控端又是自动升级的，所以：

1. **先装新的解锁服务**：在每台要从手机解锁的电脑上重新运行一遍 `install.ps1`。新服务兼容旧被控端：管道上的命令和回应没变（`STATUS`、`UNLOCK`），旧被控端不核实，照常能用，先装服务不会影响手机解锁。
2. **再升级被控端**：服务器上发布 0.9.25 及以后的被控端，或在电脑上手动升级。

顺序反了（被控端先升级了，服务还是旧的）：被控端核实不过，不会把密码发过去。手机上显示"电脑上的解锁服务要重新安装"（被控端 0.9.28 起；0.9.25～0.9.27 会显示成"没装解锁服务"），被控端日志 `host.log` 里有"管道对面不是可信的解锁服务"和原因。这时手机解不了锁，只能回到电脑前解锁，再按第 1 步重装服务。

被控端窗口里有了安装按钮以后（上面"在被控端窗口里装"），第 1 步就是在被控端窗口里点"重新安装"或"更新"。以后改了解锁服务（版本号加 1）再发布被控端，被控端自动升级后会在窗口里显示"有新版本"；管道命令不变的改动，旧服务照样能用，有空到电脑前点一下"更新"就行。改了管道命令或核实方式、旧服务用不了的，还是要按上面的顺序，先在各台电脑上更新服务，再发布被控端。

## 测试

能在本机以普通身份自动测的：

- 编译，命令同 `install.ps1`。
- 用 `--console` 模式运行，检查这些：`STATUS`；没锁屏时拒绝解锁；含控制字符的密码回 `ERR failed`；几个连上不说话的连接挡不住别的请求；同名管道已被占用时不服务、日志里有警告；占用者走后自动拿回名字。控制台模式下管道所有者是当前用户、路径也不在 Program Files，被控端的核实必须拒绝它。
- 被控端的核实逻辑和协议处理有单元测试（`host/test/unlockpipe.test.js`，Win32 层换成假的）。
- 远程桌面断开的判断、`STATUS` 的解析、`ATTACH`/`UNLOCK` 的选择、回应到错误码的映射有单元测试（`host/test/lockstate.test.js`，会话信息和管道换成假的）。
- 控制台模式下：控制台会话发 `STATUS` 回 `OK locked=… attach=0`；控制台会话发 `ATTACH` 等同 `UNLOCK`（没锁屏回 `not-locked`，锁着回 `no-service`，不输入）；`ATTACH` 的密码含控制字符、不是 Base64、为空都回 `ERR failed`。服务已经装着、占着管道名时，把源码里的管道名换一个再编译测试。
- 接回的条件判断（`RemoteSession.CanAttach`）可以单独编译一个小程序调用它：控制台会话、会话 0、不存在的会话、控制台为 `0xFFFFFFFF` 时都必须拒绝。同一个小程序（和源码一起编译、用反射调私有方法，用 `PipeServer(false)`）还可以测：失败记录按账户分开、过期清掉；`RemoteSession.RunWithin` 到时就返回、线程之后自己跑完、抛异常不崩；接回后没有 LogonUI 要等满 5 秒才回 `OK`，并且不清零失败记录；有 LogonUI 而没有锁屏事件时走输入密码那一支（测试模式在启动注入进程前就回 `no-service`，不按任何键）。不要拿真实账户和错误密码调 `CheckPassword`：会计入 Windows 的账户锁定计数。
- 窗口里安装的逻辑有单元测试（`host/test/unlockinstall.test.js`，运行脚本和问管道都换成假的）：传给脚本的参数和哈希、各个退出码、装好后的核实、版本号比较，以及改了源码没加版本号时报错。
- 打包后 `resources\unlock-service` 里有 `UnlockService.cs` 和 `install.ps1`：`npx electron-builder --win dir --config electron-builder.config.js` 打出不带安装程序的目录看一眼。

要人在电脑前点管理员确认的（自动化测不了）：

- 在被控端窗口里点"安装"或"重新安装"：确认框点"是"，窗口自动关掉，被控端日志写"装好了"，状态变成"已装好"；确认框点"否"，日志写"没能以管理员身份运行"，原来的服务不动；故意弄坏一次（比如安装时让 `C:\ProgramData\RemoteClaude` 被别的程序占着），窗口留着显示原因，按回车后日志里有退出码 1。

只能在通过远程桌面使用的电脑上测的，见下面"远程桌面接回的实测"。

### 远程桌面接回的实测

在要用的那台电脑上（新版被控端，在被控端窗口里点"更新"或用 `install.ps1` 装好新版服务）：

1. 通过远程桌面登录，启动被控端，手机能看到 Claude 窗口。
2. **断开且未锁**：直接关掉远程桌面窗口（不注销、不锁）。约 2 秒内手机显示电脑锁屏、可以解锁；被控端日志有"远程桌面已断开"。`query session` 里这个会话是"断开"，控制台是一个没有用户的新会话。
3. 手机上输入 Windows **账户密码**（远程桌面登录用的那个）解锁：几秒内回成功；电脑的显示器上出现桌面；`query session` 里这个会话变成 console、Active；手机能重新看到 Claude 窗口画面、能输入。`C:\ProgramData\RemoteClaude\unlock.log` 有"密码核对通过，把会话 N 接回控制台"，接着是"会话 N 已接回控制台（不带密码）"，或者"会话 N 已接回控制台（不带密码：…，5 秒内没到；带密码：请求已受理）"——记下这一行，它说明 SYSTEM 调用 `WTSConnectSessionW` 时要不要密码；最后是"5 秒内没有登录界面，没有锁屏"。
4. **密码错误**：重复第 2 步后输入错误的密码：回"没解开"，会话仍是断开，日志有"核对 Windows 密码没通过（错误 1326）"。输入 PIN：同样核对不过。连续 3 次后回"失败次数太多"。（可选）用密码已过期或必须改密码的账户试：手机上同样只回"没解开"，日志里是 1330 或 1907。
5. **断开前锁着**：远程桌面里按 Win+L 后关掉窗口，手机上解锁：接回后日志有"已接回控制台，但是锁着（有登录界面），接着输入密码"，最终解锁成功。
6. **正连着的远程桌面**：远程桌面开着（Active）时手机上的状态和以前一样（看屏幕锁没锁）；锁屏时点解锁应得到"失败"或"没装解锁服务"，远程桌面不能被断开。
7. **控制台上有别的用户**：（有第二个账户时）让另一个用户在电脑跟前登录着，再断开远程桌面：手机上显示锁屏、不能解锁；`unlock.log` 有"拒绝了不在控制台会话里的连接（会话 N：控制台上是别的用户的会话）"。
8. 账户类型：分别记录本地账户、Microsoft 账户、（如有）Azure AD 账户下第 3 步的结果；不通过时记下日志里的错误码。
