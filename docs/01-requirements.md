# 01 需求与范围

> 这篇是项目开始时写的需求，记录最初要解决什么问题。后来加的功能（手机审批、发文件、浏览和打开会话等）列在"功能需求"的后半段，各有单独的文档。

## 背景

用户在一台 Windows 电脑上用 Claude 桌面端同时开着多个会话，每个会话是一个独立窗口。人不在电脑前时，想用手机查看某个会话的进展并继续操作它。

现有手段都不合适：

- **ToDesk 这类整机远控**：看到和控制的是整个桌面，手机上操作多屏大桌面很吃力，也把无关内容暴露了出去。
- **飞书远程回复插件**（用户已在用）：只能回答 Claude 的提问和审批，看不到会话画面，也不能主动操作界面。
- **官方 Remote Control**：要求订阅登录且手机能访问 claude.ai，对话记录会同步到 Anthropic 服务器。

## 目标

做一个只针对 Claude 会话窗口的远控工具：在手机上选一个会话窗口，看它的实时画面，像在电脑前一样点击、滚动、打字。其它窗口看不到也控制不到。

## 使用者与环境

| 项 | 说明 |
|---|---|
| 使用者 | 起初只有用户本人；2026-11-18 起改为开放注册，每人一个账号、各管各的电脑 |
| 被控端 | 一台 Windows 11 电脑，多显示器，运行 Claude 桌面端 |
| 控制端 | 安卓手机 App（首要）；浏览器网页（已实现，作调试和备用） |
| 中转 | 使用者自己的一台云服务器（作者用的是一台香港服务器） |

## 非功能需求

下面的数值是最初定的设计目标，没有逐项正式测过；实际用下来的情况（帧率、码率、中继延迟）见 [05](05-handoff-tasks.md) 的 2.14。

| 项 | 目标 |
|---|---|
| 操作延迟 | 从点击到画面出现响应，经中继时不超过 300 毫秒 |
| 清晰度 | 按窗口原始分辨率传输，优先保清晰度，网络差时降帧率而不是降分辨率 |
| 带宽 | 默认码率上限 10 Mbps（0.8.3 起，之前 4 Mbps），可配置；只有画面大面积变化（比如滚动）时才用得到，静止时一般不到 0.2 Mbps |
| 首帧时间 | 选中会话到出现画面不超过 3 秒 |
| 可靠性 | 被控端和信令服务器断线后自动重连，无需人工干预 |
| 安全 | 见 [02 架构设计](02-architecture.md) 的安全模型一节 |

## 不做的事

第一版定的范围，划掉的是后来做了的：

- 整机桌面远控、任意窗口远控
- ~~文件传输~~（后来做了发图片、发文件，F16）、音频
- 账号之间共享电脑、权限分级（一个账号就是一个人，账号之间互不可见）
- macOS / Linux 被控端，iOS App
- 远程唤醒、~~远程解锁电脑~~（后来做了，F18）
- ~~远程剪贴板回传到手机~~：2026-11-20 做了文字的（看画面时电脑上新复制的文字自动放进手机剪贴板，协议文档 4.9）；剪贴板里的图片还不传

## 前提与约束

- **电脑必须保持解锁、不息屏**。锁屏后既采集不到画面，也注入不了输入。
- **远程操作会占用电脑的鼠标键盘**。Windows 的模拟输入只能打到前台窗口，操作时被选中的会话窗口会被切到最前。
- **Claude 桌面端的窗口特征**（2026-11 实测）：所有会话窗口属于同一个 `claude.exe` 进程，窗口类名 `Chrome_WidgetWin_1`，窗口标题就是会话名。Claude 桌面端升级后这些特征可能变化。
- **公网使用需要域名和 HTTPS**。密码、令牌和信令不加密就是明文。
- **注册和找回密码需要能发邮件**。服务器要配一个能发信的 SMTP 账号或腾讯云邮件推送。

## 术语

| 术语 | 含义 |
|---|---|
| 被控端（host） | 运行在电脑上的程序，负责采集窗口画面和注入输入 |
| 控制端（viewer） | 手机 App 或浏览器网页，负责显示画面和采集操作 |
| 信令服务器 | 运行在自己的服务器上，负责鉴权和转发连接协商消息 |
| 中继（TURN） | 双方无法直连时转发画面数据的服务，用 coturn |
| 会话窗口 | Claude 桌面端的一个会话对应的顶层窗口 |
